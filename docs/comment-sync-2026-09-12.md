# 评论双向同步验收 · 2026-09-12

本轮增加显式“同步飞书评论”入口，独立 CLI 补齐官方 `+list-comments`、`+list-replies` 单页协议。CLI、传输适配与界面分别实现并交叉审查真实文件同步和 HTTP 竞态，另用真实浏览器及专用飞书文档验证往返。

## 自动检查

- 编辑器 31 个测试文件、282 项测试全部通过，typecheck 与生产构建通过。
- 新增 63 项覆盖官方 argv/分页/回执、真实 App/Reader UI、文件持久化、HTTP 同源与 CSRF、跨进程锁、失联不重发、同步中外部改稿保留、真实 Tiptap 块偏移、配置目标隔离。
- 独立检查修复了旧组件意见挂到替换白板、已导入评论未重新核查白板身份、恢复前发送回复、分段 PUT 绕过同步忙状态及特殊回复 ID 被对象继承属性误判的问题。
- CLI 的完整 Go 测试（本机使用 external linker）、build、help 与 dry-run 通过，原有评论创建/回复/解决/恢复回归保留。

## 实际闭环

使用专用测试稿的带块 ID XML 建立隔离副本，仅复制 18 项明确引用资源；原 XML、JSON 在测试前后 SHA-256 不变。所有云调用均使用明确 bot 身份，没有登录、OAuth 或 Keychain 访问。

1. 本地按钮完整拉取 2 条云端白板评论及 1 条回复。原生组件评论定位到所属白板，未猜测内部节点 ID。
2. 在编辑模式点击“本地修订稿”组件，添加意见，XML 旁的 JSON 自动落盘并保存真实组件身份。
3. 点击同步，飞书只新增 1 条整图评论，正文包含所选组件名称；回执建立本地 ID 与 comment_id 映射。
4. 本地回复并解决该线程，再同步，真实 API 回读确认只有 1 条新增回复，状态已解决，评论没有重复创建。
5. 经独立 CLI 在云侧恢复并补充回复；本地再次同步只导入新增回复，恢复 open 状态，保留原本地组件定位。
6. 再次同步显示所有新增/回复/状态计数均为 0。Chrome 显示同一白板的意见、组件名称前缀与两条回复；本地点击引用仍高亮对应组件。

本地 XML 逐字节未变。云端 full XML 与本地的唯一差异是服务端增加 `comment-refs` 属性；移除该评论元数据后逐字节相同。不能将包含评论引用的完整响应声称为原始字节相同，也不能由本轮评论测试声称所有样式已完全适配。

私有测试配置、完整回执、测试副本与两端截图保存在忽略 Git 的 `.local/comment-sync-20260912/`；不得把其中身份和资源引用复制到公开演示稿。

## 边界

本轮同步评论、回复与状态，不上传正文、图片或白板图源。云创建粒度为全文/Docx 块；本地可以评论白板组件，但云接口内部节点锚点仍不可写。已同步评论正文的本地改写不自动覆盖原云线程；全文/已解决线程的回复限制会明确提示。写入结果不确定时暂停并保留 pending，人工或 AI 核对回执后再恢复，当前没有自动恢复按钮。
